RunPod Storage Cost Report

작성일: 2026-07-07

이 문서는 LTX-2.3 NSFW Pod를 RunPod에서 운영할 때, Container disk, Volume Disk, Network Volume 비용과 재설치 최소화 전략을 정리한 보고서다.

결론

600GB 규모의 모델, checkpoint, LoRA, workflow, output을 장기 보존해야 한다면 Volume Disk보다 Standard Network Volume이 비용상 유리하다.

추천 구조는 EUR-IS-1 Standard Network Volume 600GB에 데이터를 보존하고, Pod는 필요할 때만 생성해 실행한 뒤 종료하는 방식이다. LTX-2.3 NSFW 최초 세팅에 320GB Container disk가 필요하더라도, 이후 앱과 모델을 /workspace로 이관하면 더 작은 runtime Pod로 운영할 가능성이 있다.

주의

Volume Disk는 Pod가 stopped 상태여도 600GB 기준 월 약 $120가 계속 발생한다. 반면 Standard Network Volume은 600GB 기준 월 약 $42로, 장기 보존 비용을 크게 낮출 수 있다.

Network Volume 옵션 의미

옵션 의미 이번 운영에서의 필요도
High-performance Standard Network Volume보다 read/write가 빠른 storage 낮음에서 중간. 비용은 2배라 I/O 병목이 있을 때만 선택
Global Networking 같은 계정의 여러 Pod가 private network로 통신 낮음. 단일 ComfyUI/LTX Pod 운영이면 거의 필요 없음
S3 compatible Pod를 켜지 않고 S3 API로 Network Volume 파일 접근 높음. 모델 업로드, 백업, 파일 관리 비용을 줄일 수 있음

모델 파일을 Network Volume에 둬도 되는가

가능하다. checkpoint, LoRA, VAE, CLIP, text encoder, diffusion model 같은 모델 파일은 Container disk가 아니라 Network Volume 또는 Volume Disk에 둬도 동작한다.

중요한 것은 파일 위치 자체가 아니라 ComfyUI/LTX가 해당 경로를 알고 있는지다. 일반적으로 /workspace/models 아래에 모델을 두고, symlink 또는 extra_model_paths.yaml로 경로를 연결하면 된다. 

/workspace
  /models
    /checkpoints
    /loras
    /vae
    /clip
    /text_encoders
    /diffusion_models

권장 운영 구조

Container disk
  - Docker image runtime
  - OS / CUDA / Python 기본 환경
  - temporary files
  - logs/cache

Network Volume /workspace
  - ComfyUI / LTX 앱
  - models
  - checkpoints
  - LoRA
  - custom_nodes
  - python venv
  - workflows
  - outputs
  - scripts/start.sh

진짜로 모든 파일을 Network Volume에 넣고 Container disk를 0GB처럼 쓰는 것은 불가능하다. Docker image layer, OS runtime, CUDA/Python 기본 라이브러리, 임시 파일은 container 쪽에 필요하다. 다만 앱, 모델, custom node, venv, workflow, output을 모두 /workspace에 두면 작은 runtime Pod로 운영할 수 있다.

부트스트랩 후 작은 Pod로 전환하는 절차

  1. 최초 Pod를 docker.io/antilopax/ltx23:v9, Container disk 320GB, Network Volume 600GB로 생성한다.
  2. 최초 설치와 모델 다운로드를 완료한다.
  3. 재사용해야 하는 파일을 /workspace로 이동한다.
  4. ComfyUI/LTX의 model path를 /workspace/models 기준으로 변경한다.
  5. /workspace/scripts/start.sh만으로 실행되도록 정리한다.
  6. 현재 Pod에서 start.sh로 이미지 또는 영상 생성까지 검증한다.
  7. 새 Pod를 같은 Network Volume으로 attach하되 Container disk를 100GB로 낮춰 테스트한다.
  8. 성공하면 75GB, 50GB 순서로 낮춰 최저 안정 용량을 찾는다.

검증 명령어

현재 Pod에서 큰 파일이 어디에 남아 있는지 확인한다.

du -sh /workspace
du -sh /root /opt /usr/local 2>/dev/null
df -h

/root, /opt, /usr/local에 LTX 실행에 필요한 대형 파일이 많이 남아 있다면 이관이 아직 끝나지 않은 상태다.

최종 추천

  • 보존 storage는 EUR-IS-1 Standard Network Volume 600GB를 우선 선택한다.
  • S3 compatible datacenter를 선택해 Pod 없이 파일 관리가 가능하게 한다.
  • 최초 1회는 320GB Container disk로 부트스트랩한다.
  • 모델, 앱, custom nodes, venv, workflow, output은 모두 /workspace로 이관한다.
  • 이후 Pod는 100GB Container disk부터 테스트하고, 안정화되면 75GB 또는 50GB까지 낮춘다.
  • Volume Disk stopped 상태로 600GB를 장기 보존하는 방식은 피한다.
