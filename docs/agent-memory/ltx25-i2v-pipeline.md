Pipeline id `ltx25-i2v-two-stage` ("LTX-2.5 - I2V (two-stage, high quality)") in `src/lib/video-pipelines.ts`, workflow `workflows/ltx25-i2v-two-stage.json` (flat API-format, 43 nodes). Built from the official Lightricks two-stage distilled template — see [[ltx-subgraph-workflow-conversion]].

- **Precision: bf16** (user chose highest quality). Needs ~70GB on disk / an 80GB GPU (H100/A100-80G). Files registered in `data/model-catalog.json` (all pull from `huggingface.co/Lightricks/LTX-2.5`): `ltx-2.5-22b-dev-transformer-bf16` (42GB), `gemma4-12b-with-proj-ltx-2.5-bf16` encoder (26GB), `ltx-2.5-video-vae-bf16`, `ltx-2.5-audio-vae-bf16`, plus the 2.3 spatial upscaler. int8/nvfp4 variants also catalogued for cheaper GPUs.
- Two stages: base gen at width×height (default 960×544) then latent x2 upscale + re-sample → ~1920×1088. Audio generated + muxed by `CreateVideo` (embedsAudio:true).
- **Use the DISTILLED transformer (`ltx-2.5-22b-distilled-transformer-bf16`), NOT dev.** The official two-stage template shipped `ltx-2.5-22b-dev-...` as a placeholder default, but the workflow's fixed 8-step (+3-step upscale) schedule at CFG=1 only works with the distilled model. Dev at 8 steps produced garbled/underdenoised motion after frame 1 (frame 0 looked fine because it's the conditioned input). Verified visually: with the distilled transformer the output is coherent throughout. Official constraints: frame count 8n+1, width/height ÷32, distilled = 8-step/CFG=1 (per the LTX-2.5 model card).
- Aspect ratio is manual: set Base Width/Height to the source image's aspect (÷32); final output is 2× base. There is NO auto-aspect from the input image yet (possible future improvement via GetImageSize like the krea2 workflow).
- **Video VAE = DiffVAE (`ltx-2.5-video-vae-bf16.safetensors`), NOT conv.** The conv variant loads fine but gives a slightly painterly/noisy decode; the DiffVAE ("Diffusion Video Decoder", per the model card = industry-leading pixel quality) is much cleaner. It only loads on ComfyUI with full 2.5 support (0.32.0+); it failed on 0.30.0. Verified: a t2v mountain-lake test decoded photorealistic and clean.
- **Jumpy/popping frames on long clips** come from `VAEDecodeTiled` temporal tiling seams (default temporal_size 64, overlap 8 → a seam every ~64 frames on 30s videos). Bumped to temporal_size 80 / temporal_overlap 16 in both workflows for smoother seams.
- **Duration is the dominant quality factor.** LTX-2.5's stable range is 6–20s (best 6–10s). A 30s generation melts/degrades in segments (some frames photoreal, others "melting glass" smear) — this is the model losing coherence past its range, NOT a VAE/decode bug. Verified: a 6s DiffVAE t2v of a moving Tokyo-street POV is sharp and clean start-to-end. Fix: `applyVideoPipelineSettingsToWorkflow` (comfyui.ts) now clamps numeric controls to their [min,max], and the duration control max is 20, so 30s inputs clamp to 20. Tell users to use ≤10s for best quality; t2v (no image anchor) especially.
- **T2V pipeline** `ltx25-t2v-two-stage` (`workflows/ltx25-t2v-two-stage.json`, 38 nodes): the i2v workflow with the image branch removed (LoadImage/resize/preprocess/LTXVImgToVideoInplace deleted; EmptyLTXVLatentVideo wired straight into the concat/sampler). Same distilled transformer + DiffVAE + 8-step/CFG=1. mode:"t2v", controls drop the image-only ones. Verified end-to-end.
- Controls: seed, duration_seconds (frames = 1+floor(fps*sec/8)*8), fps, base width/height, image-cond longer side, image_guide (stage1 strength), cfg, upscale_image_guide.
- Generation runs on a RunPod ComfyUI pod (models downloaded there), not the local Mac ComfyUI (that box is only used to run graphToPrompt for conversion).
**Working pod: `onechat_ltx25_h100_001`** (podId 4ghlbke285zum3, H100 80GB), image `runpod/comfyui:cuda13.0`. Two pod-side requirements discovered by end-to-end testing:
- **ComfyUI core must include the LTX-2.5 support commits** (#15499 "Add support for LTX 2.5", #15501, #15502). The image shipped ComfyUI 0.30.0 which was ~5753 commits behind and pre-2.5 — gemma4 text encode failed (`process_tokens` returned 1 not 4) and the video VAE mismatched. Fixed by `git reset --hard origin/master` in `/workspace/runpod-slim/ComfyUI` (→ 0.32.0), preserving the baked cu130 torch (strip torch from requirements before pip install), then relaunch `python main.py --listen 0.0.0.0 --port 8188 --enable-cors-header`.
- **Use the CONV video VAE `ltx-2.5-video-vae-conv-bf16.safetensors`**, not the DiffVAE `ltx-2.5-video-vae-bf16.safetensors` — core's VAELoader builds a 3x3-conv decoder that matches the conv variant; the non-conv one fails with a decoder.conv_in size mismatch. The workflow's node 5575:5571 was switched to the conv file. Audio VAE loads fine via core VAELoader (needs metadata, which VAELoader passes). Verified end-to-end 2026-08-12: 960×544→1920×1088, 25 frames + AAC audio, ~46s for a 1s clip.

Pod ops from this repo's environment: SSH (port 22) is blocked; drive the pod via its Jupyter (port 8888, password from RunPod API pod env `JUPYTER_PASSWORD`) — kernel WS exec or contents API. See scratchpad `jexec.mjs` pattern.

- **`Lightricks/LTX-2.5` is a GATED HF repo (`gated: auto`)** → resolve URLs 401 without a token. The RunPod downloader now sends an HF token for huggingface.co URLs (added `AppSettings.huggingfaceApiKey` in settings.ts, threaded through `getRunpodDownloadPlan` in runpod.ts, plus a Settings UI field + `HF_TOKEN`/`HUGGINGFACE_TOKEN` env fallback). User must accept the gate on HF and paste a read token in Settings. The pod helper already strips `Authorization` on the CDN redirect, so no pod redeploy was needed.
